# Exact-source Go logging diagnostic replay

The optional `fast_logging_replay` input of the Go workflow is a bounded
diagnostic for one retained source/product set. It is off by default; ordinary
CI retains every original qualification step and limit.

Before executing retained products, the replay compares the actual archived
native Rust/apps/Cargo/configuration/WIT, Go SDK/compiler and complete Go build
recipe bytes with the current checkout. Added, missing, linked or changed inputs
refuse. The original logging library and installation AST must also match;
only its node configuration/tutorial fixture changes are excluded from that
compile claim. Fixed artifact IDs, run/head, sizes, metadata digests, native
binary hashes and original package-input inventories are checked.

The original five native tools freshly demo-sign the five original normal
components; the current default normal node programme must pass first. The
retained pinned Go archive and component tools then build **only** the logging
greeting through normal capture and offline compilation. The current logging
fixture runs with 14 bindings, original limits and its original four companion
builds. Compiler preparation copies and verifies the retained toolchain; it
does not bootstrap Go or rebuild native Cargo products.

`latent.go.standard-logging.replay.v1` records `compiledSource`, `fixtureSource`,
the production-byte comparison, raw original failure identities, real baseline
replay and fresh logging build separately. It never manufactures a current
normal qualification receipt or reconstructs omitted signing observations.
Fresh demo keys stay in memory. Uploads select fixed public JSON records only,
excluding raw streams, tools, private signing state and the source archive.

This experimental evidence is not production publisher authentication,
clean-host reproducibility, a release or whole-ticket qualification.
