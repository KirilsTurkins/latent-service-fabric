# Exact preparation before the Java HTTP tenant programme

The prepared tenant selection calls the normal `release prepare` command for
each exact tenant publication and its observed positive lifecycle generation.
Its reply must select that same publication, tenant, generation and component,
with `prepared: true` and `executionAuthorized: false`. This setup operation
does not invoke the guest or add a provider grant.

Only this setup command selects the bounded 300,000 ms control RPC allowance
and 305-second owned process allowance. The existing process owner clips that
wait to the original campaign deadline. The node and both real HTTP peers keep
their original 300-second whole lifetime; the clock is never reset. Every later
invocation keeps its original 120,000 ms RPC timeout, execution budget and
provider limits. All twelve original outcomes and ten-contact peer assertions
remain mandatory. The default tenant selection performs no new setup command.

The reason for separating compilation from invocation is the retained failed
tenant programme at source `821b7ac39148ba1c5a6f3ed74761f018bb50e160`,
run `39495294735`, job `118878696130`. Its first authorized call expired after
120 seconds with an uncertain result, queued activation and no HTTP contacts;
prior cold compilation took approximately 104 seconds. That failure remains a
failure. The controller neither retries its mutation nor reuses its node.

Seven source controls cover the exact setup command, original deadline clipping,
lossless lifecycle generation, foreign/stale/refused selection, preserved
failure results and explicit selection. They run alongside the eight existing
tenant controls. No current native preparation or signed tenant pass is claimed
until a source-authenticated preparation producer and the actual twelve-case
programme succeed.
